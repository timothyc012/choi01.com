# Source and runtime checks

## Current source and release

Read the website repo's `docs/mohemeokji-recipe-source.md`. Discover active connection/container, database and tenant; compare sample Recipe/IngredientQuantity/CookingStep records and current source hashes. The last confirmed recipe corpus was q6 personal `onto_personal`, not the retired combined DB or company DB. Reconfirm it rather than hardcoding that observation or an old port. Read identifiers without printing credentials.

The reviewed adapter accepts only three hash-pinned SQL files, uses read-only transactions and current tenant-scoped `fact` relationships, batches discovery identities, and bounds results at 500 per identity/5,000 selected unique recipes. A query failure or overflow is a failure, not a silently truncated successful export. Keep private SSH JSON outside the repo/public tree. A URL ending in a recipe ID proves identity linkage, not instruction fidelity, complete inventory or German availability.

For each selected dish retain original ID/title/author, servings, ingredient quantities, ordered steps, source time and current content hash. Align required steps with the ingredient inventory, distinguish optional accompaniments, raw/cooked/canned states and exact cuts/species. Do not fabricate missing instructions, durations or gram weights. A fresh export is not equivalent to having re-fetched every original website.

Use governed `meal:release prepare` with explicit database/tenant. Bootstrap is only the first immutable release; rollover retains the previous tree and correction retains the current same-week chain. Verify twin bytes, pointers, every artifact hash, CSV/coverage and discovery provenance, all locations, exact offer boundaries, mode readiness and asset budgets. Include the hashed discovery and nutrition catalogs when present. Public payloads contain no private queue, raw source body, reviewer identity or private lineage. Record approved source/hash/transform identity and do not substitute an old registry approval after source drift.

The public snapshot approval digest is mandatory. Do all source review, calculations, tests/build/typecheck/sync, UI checks and a concrete review report before asking the owner to approve it. Tests that read `public/` must run in an isolated private candidate checkout populated from the sealed staging tree; unchanged published data is not candidate QA. Keep the original public tree and sealed receipt inputs untouched. Do not publish data, activate MCP, or upload a release package to an external host before that exact approval. Missing price or nutrition evidence remains visible; an unavailable mode cannot borrow balanced recommendations.

## Test scenarios

1. CSV/coverage: intended Monday–Sunday, new real postcodes, all previous coverage branches, UTF-8 BOM, malformed/conditional prices, branch collisions, duplicate rows, missing evidence, unpublished/inaccessible/zero branches. Processing 72 pages is not reviewing 72 pages; empty text pages require visual/OCR evidence. Never fill absent current offers from last week.
2. Source identity: prepared chicken is not raw meat; breast/tenderloin and pork/beef cuts remain distinct; stock/unknown processed ingredients block unsupported vegetarian claims. Butternut/Buttermilch are not butter. Fresh-herb source exclusions must ignore review-author contamination.
3. Quantities/prices: source 300g scales to the selected servings only when original servings are known; 1.3kg at a verified 1kg pack needs two packs and two such meals need three. `je 100g` is a weight quotation and requires actual purchase weight, not an invented pack. Variant ranges, `약간`, missing/conflicting servings and unresolved denominators show manual-check state. Individual recipe checklist additions are idempotent max counts; the weekly basket sums measured requirements. Unknown quantities/prices prevent a complete basket total.
4. Nutrition: complete, estimated, partial and unknown are distinct. Check all four nutrients, full inventory, source food/preparation/basis/hash, reference conversion provenance and scenario disclosures. Partial sums do not enable nutrition/diet. The general nutrition catalog may supply approved mains with `sale_linked=false` and missing price; sides never enter automatic lunch/dinner. User grams remain local nutrition scenarios and survive only the same recipe/source hash; they must not alter shopping or MCP/DB facts.
5. Persistence/conditions: save, switch lunch/dinner and supermarket, return and reload. Vegetarian/exclusion settings affect cards, automatic modes, manual additions, drop and replacement. Pantry/checklist survive rollover while stale manual prices/selling units are invalidated. Do not claim shared household stock quantity. Planning a dish is not eating it; explicit eaten history persists across stores and expires after 14 days.
6. Routing/eligibility: existing paths with/without slash, valid/invalid query combinations, one-chain and new postcodes. Balanced/price automatic candidates need an active defining offer for that exact branch/date; ordinary manual/nutrition candidates are labelled separately. Compare eligible source IDs and counts, not just first-card order. No duplicate/self alternatives in sparse pools, truthful empty state, old saved dishes accessible with no-current-discount/conflict labels.
7. Real browser: CUA at 1280×900, 390×844 and 320×844 against actual static paths. Test all manifest locations plus one complete and one sparse/zero store deeply: four modes, lunch/dinner, real mouse card drag/drop, button placement, X/clear, Plan/Menu/Shop navigation, detail/source failure, pantry/checklist, reload and saved-plan rollover. Capture screenshots and console/network evidence. Initial snapshot data is pointer/manifest/selected location, with pinned catalogs on demand and lazy details; no CSV/private queue/unrelated location shard requests. CUA unavailable/locked is a failed browser gate; no raw Playwright/CDP or lock bypass.
8. MCP: record all live tool names and auth/profile first. Last confirmed baseline was 24, not the historical 8/13/18 counts. Preserve every name and unrelated auth/action/study module. Replay limit 20 plus next offset, date, vegetarian/exclusions, general estimated nutrition, exact source/selected servings, hash failure and anonymous 401. Ordinary weekly data uses verified remote snapshot artifacts; runtime changes need reviewed meal-only overlay on the fresh live baseline, not an older whole image/wheel.
9. Deployment: no unrelated dirty build, vendor-guard bypass, fake fingerprint or historical asset mutation. Verify actual target source bytes, full release build/test/typecheck/sync, retained rollback inside the same data root, committed/deployed pointer/manifest/location and every changed asset hash. Production read-only smoke is separate from local replay. Do not claim latest main passed when only a reviewed isolated production-base overlay was built.

## Scope to disclose

The website/MCP publish selected reviewed static catalogs, not live full-DB search, live shelf stock or ordering. Counts change with current evidence. Pantry is checkbox ownership per store rather than measured shared stock. Source-based serving scaling handles only known quantities; nutrition conversions do not establish a shopping yield. Official general prices need separately collected branch/date evidence. Nutrient-input estimates and quantity scenario bounds do not prove personal nutritional adequacy. Source subset purging, original archive cleanup and graph acknowledgment are separate owner maintenance operations.
