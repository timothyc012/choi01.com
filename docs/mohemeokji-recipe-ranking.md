# 모해먹지 레시피 선별·추천 기준

## 온톨로지 보존 레시피 30,000건

수집 후보는 먼저 `recipe_id`로 중복 제거한다. 같은 ID가 여러 번 수집된 경우 후기 수, 평점, 재료·단계 메타데이터가 더 충실한 행을 남긴다. 중복 제거 후 다음 품질 점수로 정렬해 상위 30,000건만 온톨로지에 적재한다.

```text
보정평점 = (원문평점 × 후기수 + 4.5 × 20) / (후기수 + 20)
평점점수 = clamp((보정평점 - 3.5) / 1.5, 0, 1) × 18
후기점수 = min(log(1 + 후기수) / log(1001), 1) × 12
품질점수 = 평점점수 + 후기점수
```

후기 1개의 5.0점이 후기 180개의 4.8점보다 앞서지 않도록 Bayesian 평균과 로그 후기 신뢰도를 함께 쓴다. 평점이나 후기 수가 없는 레시피의 품질점수는 0이다. 동점이면 후기 수, 원문 평점, 단계 수, 재료 수 순으로 비교한다.

선별 manifest에는 후보 수, 평점 보유 후보 수, 보존·제외 건수와 보존 ID 목록의 SHA-256을 기록한다. 전체 후보 원문은 검증이 끝난 뒤 삭제하고, 선별된 30,000건과 감사 manifest만 유지한다.

2026-09-12 정리 결과는 원시 행 76,091건에서 중복 5,829건을 제거해 고유 후보 70,262건을 만들고, 필수 식별자가 없는 34건을 제외한 뒤 상위 30,000건을 보존한 것이다. 나머지 고유 후보 40,262건과 중복·임시 수집 디렉터리는 삭제했다. 현재 `01ontology-open/data/sources/recipe`에는 최종 `recipes.jsonl` 한 개와 감사 manifest만 있으며, 레시피 ID도 30,000개 모두 고유하다.

최종 30,000건은 모두 원문 평점과 후기 수를 가진다. 다만 현재 원천 데이터에서 이 30,000건의 평점이 모두 5.0으로 수집되어, 이 집합 내부의 실제 순위 차이는 Bayesian 보정 뒤 후기 수 신뢰도가 주로 만든다. 평점 값을 서로 다른 수준으로 비교하려면 원문 평점 파서의 분포를 별도로 재검증해야 한다.

활성 적재 대상은 `recipe-30k-v2`이며 레시피 30,000건, 평점 30,000건, 후기 수 30,000건, 외부 참조 30,000건을 검증했다. 이전 `recipe-30k`와 `recipe-30k-smoke` 테넌트는 append-only 감사 정책 때문에 물리 삭제하지 않고 과거 이력으로 남겼으며, 추천에서는 새 활성 테넌트만 사용한다.

## 웹 카탈로그 100건

기존에 원문 단계를 검수한 52건은 저장 식단 호환을 위해 유지한다. 추가 48건은 보존된 30,000건 중 현재 할인 데이터에 정확히 연결할 수 있는 주재료를 가진 식사 메뉴만 고른다. 바나나·요거트 같은 간단식 재료는 자동 추가 대상이 아니다. 한 재료군으로 쏠리지 않도록 재료군별 품질 순위를 만든 뒤 라운드 로빈으로 채운다.

추가 48건은 온톨로지의 제목, 원문 URL, 작성자, 재료, 평점·후기, 조리시간과 단계 수 메타데이터만 사용한다. 조리 단계 본문을 수집하지 않은 항목은 내용을 만들지 않고 원문 링크 확인 상태로 표시한다.

## 주간 추천 점수

레시피가 점심·저녁 추천 후보가 되려면 선택한 우편번호·마트에서 현재 유효한 `주재료` 행사가 최소 1개 있어야 한다. 이 조건은 평점이 아무리 높아도 우회할 수 없다.

```text
추천점수 = 할인 주재료 일치율 × 100
         + 매장 특이성
         + 부재료 할인(최대 9)
         + 평점·후기 품질점수(최대 30)
         - 조리시간 패널티(최대 15)
         - 간단식·반찬 패널티
         - 최근 14일 동일 레시피·재료군 반복 패널티
```

주간 식단을 구성할 때는 같은 재료군을 최대 2회로 제한하고, 바로 앞 메뉴와 같은 재료군을 피하며, 이미 많이 쓴 조리법에도 추가 패널티를 준다. 후보가 부족하면 할인과 무관한 메뉴로 일곱 칸을 강제로 채우지 않는다.
