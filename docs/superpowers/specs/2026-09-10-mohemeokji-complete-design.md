# 모해먹지 주간 레시피 시스템 완성 설계

**승인된 방향:** 매장별 주간 스냅샷, 네 가지 추천 모드, 계획/장보기 분리 UI

**기준일:** 2026-09-10

**제품 기록:** `PRODUCT.md`

## 문제

현재 `recipe-full`에는 72,569개 레시피가 있지만 사이트는 수동 검토한 52개만 정적 파일에 보관한다. 현재 할인상품과 일치하는 후보가 52064 EDEKA에서만 1,035개인데 화면에는 12개만 나타난다. 후보 조회 스크립트는 검토용 JSON을 만들 뿐 게시 데이터로 이어지지 않으며, 상품 재료 키마다 최대 20개까지만 반환한다. 사용자는 실제 선택 폭, 추천 근거, 목적별 정렬을 기대하지만 현재 구조는 이를 충족하지 못한다.

완성된 시스템은 72,569개를 브라우저에 싣거나 모두 AI로 처리하지 않는다. 매주 할인상품에 해당하는 가벼운 후보 메타데이터만 데이터베이스에서 찾고, 품질·인기·다양성 기준을 통과한 소수의 전체 레시피만 내보내 검토한 뒤 매장별 정적 스냅샷으로 게시한다.

## 선택한 접근과 거절한 접근

### 선택: 빌드 시점의 매장별 스냅샷 컴파일러

동일한 입력 CSV, 데이터베이스 기준시점, 정책 버전으로 같은 바이트를 재생성할 수 있는 컴파일러를 만든다. 브라우저는 선택한 매장 스냅샷만 지연 로드하고 로컬의 보유 재료·먹은 기록·추천 모드에 따라 순서를 계산한다.

### 거절: 전역 레시피 파일을 계속 수동 확대

작은 수정으로 보이지만 매주 사람의 복사 작업이 반복되고, 상품 상태·출처·수량 정합성이 다시 어긋난다.

### 거절: 72,569개 전체를 브라우저로 전송

초기 다운로드와 검색 비용이 크며, 원문 조리단계 공개 범위와 출처 변경을 통제하기 어렵다. 사용자에게 필요한 것은 전체 DB 덤프가 아니라 현재 매장의 신뢰할 수 있는 선택지다.

### 거절: 72,569개 전체를 매주 AI로 평가

시간과 모델 비용이 불필요하게 크다. SQL과 결정론적 점수로 후보를 줄이고, AI 또는 사람이 필요한 작업은 새로 선택되거나 원문 해시가 바뀐 레시피의 조리법 재서술에만 사용한다.

## 전체 데이터 흐름

```text
Aside 주간 CSV + coverage.csv + regular_prices.csv(있는 범위)
  → CSV 구조·기간·지점·가격 조건 검증
  → 모든 유효한 행사 행을 정확한 음식 identity로 정규화
  → recipe-full에서 현재 행사 identity의 후보 메타데이터 조회
  → 원문 품질·보정 인기도·다양성으로 매장별 후보 선정
  → 선정된 고유 레시피만 전체 재료량·단계·출처 조회
  → 승인된 한국어 조리법 재서술과 영양 근거 결합
  → 동일 입력 이중 생성 및 바이트 비교
  → 불변 주간 스냅샷 게시
  → 브라우저에서 매장·모드·보유 재료·최근 식사로 최종 정렬
```

## 1. 행사상품 identity

현재처럼 한 재료 키에서 첫 번째 일치 행만 택하지 않는다. 모든 유효한 행사 행을 보존하고 안정적인 `offerId`를 만든다.

```js
{
  offerId,
  postcode,
  chain,
  branchId,
  sourceRow,
  evidenceUrl,
  validFrom,
  validThrough,
  productDe,
  pack,
  priceCents,
  normalPriceCents,
  conditions,
  autoPriceEligible,
  identity: {
    ingredientId,
    species,
    cut,
    processingState,
    form,
    composition
  }
}
```

`닭가슴살`, `닭안심`, `돼지안심`, `돼지목살`, `돼지등심`, `돼지뒷다리살`, `돼지다짐육`, `소·돼지 50/50 다짐육`, `생연어`, `훈제연어`, `슬라이스 가공치즈`는 별도 identity다. `substitution`은 설명에만 사용할 수 있고 추천 자격이나 가격을 만들지 않는다.

## 2. 72,569개 후보 축소

### 2.1 가벼운 DB 검색

매주 전체 조리법을 읽지 않는다. 행사 identity에 연결되는 레시피 ID, 제목, 평점, 후기 수, 단계 수, 인분, 재료 identity와 계량 여부만 조회한다.

- identity당 최대 500개
- 주간 전체 최대 5,000개
- 한도를 넘으면 실제 전체 개수와 잘린 개수를 감사 보고서에 기록
- 재료 identity가 추천 자격을 만들며 제목 일치는 순위 보조 신호일 뿐 자격을 만들지 않음

### 2.2 필수 품질 관문

다음 조건을 모두 통과해야 공개 후보가 된다.

- 안정적인 source recipe ID, 원문 URL, 제목, 작성자 존재
- 재료 최소 2개와 연속된 조리단계 최소 3개
- 주재료가 레시피에 실제 존재하고 상품의 부위·상태·형태와 충돌하지 않음
- 주재료 수량이 원문에 명시됨. 계량 불가능한 단위는 원문 문자열을 보존하고 수량 상태를 `unknown`으로 표시
- 단계 번호가 중복·누락되지 않고 숫자 순으로 복원됨
- 같은 source ID와 정규화 제목 중복 없음
- 현재 원문 해시에 승인된 공개용 한국어 재서술이 존재

### 2.3 후기·평점 보정 점수

평점 5.0에 후기 1개인 레시피가 후기 수백 개의 4.9점보다 자동으로 앞서지 않게 Bayesian 보정을 사용한다. 현재 데이터의 검증값은 전체 평균 평점 `4.918`, 후기 수 중앙값 `108`, 평점 범위 `4.5–5.0`, 최대 후기 수 `2,721`이다. 값은 주간 정책에 하드코딩하지 않고 데이터 기준시점에서 산출해 manifest에 기록한다.

```text
adjustedRating =
  reviewCount / (reviewCount + priorStrength) × rating
  + priorStrength / (reviewCount + priorStrength) × globalMeanRating

popularity = log(1 + reviewCount) / log(1 + maxReviewCount)

qualityScore =
  0.65 × normalizedAdjustedRating
  + 0.25 × popularity
  + 0.10 × sourceCompleteness
```

`priorStrength`의 v1 값은 해당 데이터의 후기 수 중앙값이다. 평점 또는 후기 수가 없으면 0으로 대체하지 않고 `qualityStatus: partial`로 표시한다. 이 후보는 균형 모드의 후순위에는 들어갈 수 있지만 `인기순`이라는 설명을 받을 수 없다.

### 2.4 매장별 게시 구성

가용한 후보가 충분한 매장의 목표는 48개다.

- 식사 36개
- 아침·간단식 최대 6개
- 반찬 최대 6개
- 각 행사 주재료에서 먼저 식사 최대 2개 확보
- 주재료 하나당 최대 6개
- 음식 family당 최대 8개
- 조리법 method당 최대 12개
- 작성자당 최대 4개
- 최소 품질을 유지하면서만 제한을 결정론적으로 완화하고 완화 이유를 기록

후보가 부족하면 숫자를 채우기 위해 부위·상태·출처 조건을 완화하지 않는다. 1–20개의 식사만 있으면 실제 개수와 부족 이유를 표시하고, 0개면 할인상품 탐색과 장보기는 유지하되 자동 식단을 만들지 않는다.

## 3. 공개 스냅샷

```text
public/mohemeokji/data/
  current.json
  snapshots/<week-start>/<snapshot-id>/
    manifest.json
    coverage.json
    locations/<postcode>/<store>/<branch-id>.json
    recipes/index.json
    recipes/<source-recipe-id>.<content-hash>.json
```

`current.json`은 모든 검사를 통과한 불변 스냅샷만 가리킨다. manifest는 스키마·생성기·선택·영양 정책 버전, Europe/Berlin 주간, 원본 CSV 및 DB export 해시, tenant, 지점 identity, 모든 파일 해시, 매장별 행사·후보·게시·자동 식사 수, 미연결 상품과 경고를 포함한다.

위치 파일은 offer와 recipe ID 및 정확한 match 관계만 가진다. 레시피 상세 파일은 source ID로 공유해 여러 매장에서 중복 저장하지 않는다. 브라우저는 현재 위치 목록과 첫 추천 상세만 먼저 읽고 나머지 상세는 열 때 불러온다. 이전 두 주의 스냅샷과 참조된 레시피 상세는 저장 식단 복구를 위해 유지한다.

## 4. 원문과 공개 조리법

원문 단계는 private staging에서만 처리한다. 공개 registry의 키는 `recipeId + sourceContentHash + transformVersion`이다. 단계 순서와 필수 행위를 보존한 한국어 재서술만 게시하며, 원문 이미지·HTML·긴 원문 문장은 복사하지 않는다. 원문 해시가 바뀌면 이전 승인은 무효가 되고 재검토 전까지 해당 레시피를 건너뛴다.

공개 레시피는 원문 ID·제목·작성자·URL, 원문 재료명과 수량 문자열, 인분·시간, 공개 단계, offer match, 영양 및 가격 완성도, 변환 버전과 출처 해시를 가진다.

## 5. 추천 모드

한 번에 하나의 모드를 native radio group으로 선택한다. v1은 가중치 슬라이더를 제공하지 않는다.

### 균형

정확한 할인 주재료, 조리시간, 최근 14일 먹은 기록, family·method 다양성을 함께 본다. 가격·영양 데이터가 불완전해도 사실을 숨기지 않고 후보가 될 수 있다.

### 가성비

선택한 인분에서 보유 재료를 제외한 **장바구니 구매금액**이 완전한 메뉴만 비교한다. 판매 포장 전체를 사는 현금 지출을 사용하며 섭취한 재료 원가라고 부르지 않는다.

```text
singleMealCost = complete target-serving basket outlay
weeklyMarginalCost = basket(선택된 식단 + 후보) - basket(선택된 식단)
```

정상가가 같은 상품·포장·마트 근거로 확인된 경우에만 절감액을 별도로 보여준다. 정상가가 없으면 구매금액 순위는 가능하지만 절감액은 `확인 불가`다. 가격 또는 포장 수량이 하나라도 미확인이면 가성비 비교에서 제외하고 이유를 보여준다.

### 영양

원문 인분과 주요 재료 중량, kcal·단백질·식이섬유·나트륨 근거가 모두 있는 메뉴만 비교한다. 기존의 재료당 100g 가정값은 안내용 추정에만 남기고 순위에는 사용하지 않는다.

v1 비중은 열량 범위 20%, 단백질 30%, 식이섬유 30%, 나트륨 20%다. 목표값과 출처·적용일은 versioned `nutritionPolicy`에 둔다. 합성 점수 대신 사용된 1인분 수치와 완성도를 사용자에게 보여준다.

### 다이어트

개인 의료·체중 감량 처방을 하지 않는다. 일반적인 낮은 열량 밀도와 충분한 단백질·식이섬유를 찾는 탐색 모드다. v1 비중은 낮은 열량 40%, 단백질 30%, 식이섬유 20%, 나트륨 10%다. 원문 인분 또는 영양 근거가 불완전하면 순위에서 제외한다.

### 모든 모드의 공통 규칙

- 선택한 매장의 현재 유효한 정확한 주재료 offer가 필수
- 점심·저녁 자동 식단은 main만 사용
- 같은 source recipe ID는 한 주에 한 번만 사용
- 최근 먹은 동일 메뉴와 family를 감점
- family당 최대 2회, 가능한 경우 연속 family 금지, method 반복 감점
- 모드 비교 가능 후보가 부족하면 빈 칸을 유지하고 `비교 가능한 메뉴 3개만 채웠습니다`처럼 설명
- 모드를 바꾸면 자동 슬롯만 다시 계산하고 직접 선택한 슬롯은 보존

## 6. 인분과 데이터 완성도

추천 설정에 `몇 인분 기준`을 둔다. 최초 기본값은 2인분이며 1–6인분을 선택하고 전역 사용자 선호로 보존한다.

```text
scaledAmount = sourceAmount × targetServings / sourceServingCount
packageCount = ceil(scaledAmount / packageAmount)
nutritionPerServing = wholeRecipeNutrition / sourceServingCount
```

각 계산은 `source`, `converted`, `estimated`, `partial`, `unknown` 상태와 근거를 가진다. `partial` 또는 `unknown`은 0으로 계산하지 않는다.

## 7. UI: 계획 모드와 장보기 모드

### 전역 구조

```text
모해먹지
├── 출처 바: 우편번호 · 마트 · 지점 · 행사주간 · 근거 상태
├── 계획 | 장보기 전환
├── 계획
│   ├── 추천 기준: 균형 · 가성비 · 영양 · 다이어트 · 인분
│   ├── 대표 추천과 근거
│   ├── 레시피 탐색·검색·비교
│   ├── 월–일 × 점심·저녁 14칸
│   └── 보유 재료 편집
└── 장보기
    ├── 남은 품목·금액
    ├── 미구매 목록
    └── 구매 완료 목록
```

Desktop은 왼쪽 레시피 ledger와 오른쪽 7×2 식단을 함께 보여준다. 모바일은 `메뉴`, `식단`, `장보기` 하단 탐색으로 한 작업씩 보여준다. 장보기 모드는 계획용 설명을 숨기고 큰 체크 영역, 포장 수, 독어명, 남은 금액을 엄지 범위에 고정한다.

카드 중첩을 줄이고 정렬된 행과 구분선을 사용한다. 메뉴의 핵심 근거는 다음 한 줄이다.

```text
독어 상품명 · 판매 단위 · 할인가 · 지점/행사주간 · 근거 상태
```

대표 추천은 모드에 따라 `왜 이 메뉴인지`를 합성 점수가 아니라 실제 사실로 설명한다. 사용자가 직접 고른 메뉴에는 `1순위 추천`을 붙이지 않는다.

### 주간 슬롯의 X 동작

주간 식단의 `×`는 닫기나 삭제가 아니라 **현재 후보 거절 후 다음 메뉴 보기**다. 시각적으로 `× 다른 메뉴` 의미를 드러내고 접근성 이름은 `월요일 저녁의 소고기 찹스테이크를 제외하고 다음 후보 보기`처럼 지정한다. 완전히 비우는 동작은 별도의 `비우기` 메뉴로 제공한다.

동작 순서:

1. 현재 recipe ID를 해당 슬롯의 `dismissedRecipeIds`에 추가한다.
2. 현재 모드·마트·식사시간의 적격 후보에서 이미 주간에 사용한 ID와 해당 슬롯에서 거절한 ID를 제외한다.
3. family·method·최근 식사 다양성 규칙을 적용해 다음 1개를 선택한다.
4. 다음 후보가 있으면 같은 슬롯에 즉시 교체하고 근거·장바구니 합계를 갱신한다.
5. 후보가 없으면 슬롯을 비우고 `이 조건에서 다음 후보가 없습니다`를 알린다. 자동으로 다른 모드나 다른 마트의 메뉴를 넣지 않는다.

X로 받은 다음 후보는 `origin: auto`를 유지하므로 새 주간 스냅샷이나 모드 변경 때 갱신될 수 있다. 레시피 목록에서 사용자가 직접 넣은 메뉴는 `origin: manual`이다. 거절 목록은 슬롯마다 최대 20개를 보존하며 스냅샷이 바뀌면 비운다.

## 8. 저장 상태 v2

```js
{
  schemaVersion: 2,
  area,
  store,
  branchId,
  weekStart,
  snapshotId,
  mode,
  targetServings,
  moments: {
    점심: {
      mon: {
        recipeId,
        origin: "auto" | "manual",
        dismissedRecipeIds: []
      }
    }
  }
}
```

- 같은 스냅샷에서는 모든 유효 슬롯 복원
- 새 스냅샷에서는 auto 슬롯과 dismissed 목록만 다시 계산
- manual 슬롯과 사용자가 명시적으로 비운 슬롯 보존
- 추가·드래그·대표 추천 확정은 manual, 자동 식단과 X 교체는 auto
- legacy v1 슬롯은 출처를 추론할 수 없으므로 manual로 이전
- 먹은 기록은 source ID 기준으로 매장·모드와 독립 유지
- 보유 재료와 체크 상태는 유지하되 지난 가격·포장·수량 override는 기존처럼 무효화
- 오래된 manual 레시피는 이전 recipe shard로 열고 `현재 주재료 할인 없음` 표시

## 9. 오류와 부족 상태

- CSV 또는 DB 실패: `current.json`을 바꾸지 않고 이전 주간을 `지난 자료`로 표시
- 모호한 상품 identity: 상품 목록에는 남기되 자동 레시피·가격에는 연결하지 않음
- 후보 0개인 행사상품: `연결 레시피 0개`와 거절 이유 분포 표시
- 모드 비교 후보 0개: 다른 모드로 몰래 전환하지 않고 `균형 추천 보기` 제공
- 가격·영양 부분 데이터: 확인된 값과 미확인 항목 수를 분리
- 손상된 스냅샷: 다른 지점 데이터를 대신 사용하지 않고 명시적 불러오기 오류 표시
- 지난 저장 식단: 현재 주간으로 자동 해석하지 않고 `현재 할인으로 새로 짜기`, `지난 식단 유지`, `비우기` 제공

## 10. 재현성과 성능

- 행·키·지점·후보·레시피 ID를 canonical sort
- 입력 수집시각과 DB 기준시점을 사용하고 생성 시각은 순위·해시에 넣지 않음
- 동일 입력을 별도 임시 디렉터리에 두 번 생성해 모든 바이트 비교
- 원본 CSV SHA와 정규화 데이터 SHA를 따로 기록
- 선택 매장 위치 파일 목표 60KB 이하, 개별 레시피 상세 12KB 이하
- 초기 압축 전송 목표 120KiB 이하
- 모바일 LCP 2.5초 이하, INP 200ms 이하, CLS 0.1 이하
- audit CSV는 브라우저가 내려받지 않음

## 11. 검증

자동 검증은 다음 축의 조합을 포함한다.

- manifest의 모든 지점, 현재 11개 조합
- 균형·가성비·영양·다이어트 × 점심·저녁
- 1280×900 desktop과 390×844 및 320px mobile
- 현재·미래·만료·빈 데이터·후보 1개·반찬만 있음·7개 미만
- exact/substitution 및 부위·상태·혼합비 충돌
- 평점 5.0 후기 1개와 평점 4.9 후기 수백 개의 보정 순위
- 가격·정상가·인분·영양 완성도와 unknown≠0
- X 연속 교체, 중복 방지, 후보 소진, 슬롯별 거절 목록, snapshot reset
- v1→v2 이전, auto/manual 보존, 모드 전환, 오래된 manual 레시피
- 검색·필터·레시피 상세·독어명·출처 링크·보유 재료·포장 수·주간 합산·체크 왕복
- legacy route, query route, 잘못된 위치 fallback, 신규 우편번호
- 키보드 전용 전체 흐름, focus 복원, live region, 44px target, 200% zoom, console/network 오류 없음

배포 전에는 manifest/schema 검증, 입력 동일성 이중 빌드, 테스트 결과, 매장별 후보/게시/자동 수, 모바일·데스크톱 화면, 접근성·성능 결과, 배포 파일 해시를 보존한다.

## 12. 단계적 출시와 롤백

1. 행사·레시피 identity와 versioned schema를 먼저 도입한다.
2. 전체 후보 조회와 rich export를 만들고 기존 주간으로 shadow compile한다.
3. 매장별 스냅샷 compiler와 공개 재서술 registry를 도입한다.
4. 52064 EDEKA를 비기본 snapshot URL에서 검증한다.
5. 저장 상태 v2와 균형·가성비를 먼저 연결한다.
6. 계량·영양 근거가 준비된 메뉴에만 영양·다이어트를 활성화한다.
7. 계획/장보기 UI와 X 다음 후보 동작을 공개한다.
8. 11개 지점 검증 후 `current.json` 포인터를 전환한다.
9. 두 번의 성공적인 주간 게시 후 52개 legacy 경로를 제거한다.

이전 두 주 스냅샷과 이전 앱 asset을 유지한다. 롤백은 실패 스냅샷을 삭제하지 않고 상태를 `withdrawn`으로 기록한 뒤 `current.json`과 앱 asset을 직전 manifest로 되돌리는 방식이다. 수동 식단은 유지하고 auto 슬롯만 직전 snapshot에 맞게 재계산한다.

## 범위 밖

- 실시간 매장 재고 또는 계산대 가격 보장
- 개인 의료·질환·체중 감량 처방
- 근거 없는 정상가·절감액·영양값 생성
- 72,569개 원문 전체 공개 또는 브라우저 전송
- 여러 마트의 최저가를 섞은 하나의 장바구니
- 사용자가 승인하지 않은 스케줄 변경 또는 자동 배포 생성
