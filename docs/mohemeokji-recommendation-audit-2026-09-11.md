# 모해먹지 추천 근거 감사와 다음 알고리즘

## 확인된 사실

- `01ontology` DB, `recipe-full`의 Recipe `6875875`에는 `reviewCount=1077`, `ratingValue=4.9`가 실제로 저장돼 있다. 값이 없는 경우가 아니라, 필드 의미를 신뢰할 수 없는 경우다. DB는 읽기 전용으로 확인했으며 변경하지 않았다.
- `01ontology-open/scripts/crawl_10000recipe.py`의 `_parse_rating`은 HTML 전체를 줄로 바꾼 뒤 처음 일치하는 `4.9(숫자)`를 채택한다. 현재 레시피와 하단 추천 레시피의 경계를 검사하지 않는다. `import_10000recipe.py`는 그 숫자를 Recipe의 `reviewCount`에 넣는다. 원래 수집한 HTML이 없으므로 당시 1,077이 어느 추천 카드였는지까지는 입증하지 못했다.
- 2026-09-11 원문 확인: 사과컵밥의 Recipe JSON-LD에는 aggregateRating이 없고, 본문에 요리 후기 수가 없다. 댓글은 0이다. 조회수는 후기 수가 아니다. UI는 `리뷰 수 미확인`으로 표시한다.
- 닭가슴살죽 `6872321`은 본문 `요리 후기 6`, Recipe JSON-LD `reviewCount=6`, `ratingValue=5`가 일치한다. 댓글 4는 별도다.
- 게시 중인 81개 원문을 각각 확인했다. 25개는 요리 후기 수 확인, 56개는 요리 후기 수 미공개다. 미공개를 0으로 바꾸지 않는다. 상세별 SHA-256, 원문 URL, 확인 시각, 응답 해시와 검증 방식을 `data/mohemeokji/verified-reviews.json`에 기록했다.
- ALDI Nord 44369 CSV에는 10행이 있고, 모두 KaufDA 기사 한 개를 출처로 삼는다. 독어 상품 매칭을 통과한 것은 요거트 1종이다. 소시지·Grillhaxe·Sauerkraut·머스터드·Schnitzel·Leberkäse·푸딩·무스·바가 남는다. 10행은 전체 전단 조사를 증명하지 않으며, 1종은 마트 전체 행사 수가 아니다.

## 현재 추천의 결함

1. 후보 조회 SQL, 후보 상한 적용, 100개 후기 문턱, 정적 게시 점수가 모두 신뢰할 수 없는 DB 수치의 영향을 받는다. 화면에서 숫자만 숨겨도 후보 풀은 바로잡히지 않는다.
2. 정적 게시 점수와 화면 추천 순서는 서로 다른 계산이다. 브라우저 균형 추천은 할인 재료 비율·다양성·기록을 사용하며 `qualityScore`를 실제 정렬에 쓰지 않는다. 지금 목록을 '7만 개 중 후기 상위'라고 설명하면 안 된다.
3. 레시피 이름을 정한 뒤에도 `kind`가 main으로 남아 디저트·음료·빵이 점심·저녁에 들어갈 수 있다. 영양 모드는 정확한 1인분 영양값이 없으면 계산할 수 없다.
4. 사과/요거트가 포함됐다는 이유와 그 재료가 요리를 정의한다는 판단을 더 엄격하게 구분해야 한다. 허니애플 스테이크의 사과 소스는 일반적인 고기 할인과 동일한 경제적 의미를 갖지 않는다.
5. 제목에 고기가 안 보인다는 이유로 채식이라고 하면 굴소스·육수·젤라틴 등을 놓친다. 이번 변경에서는 이 자동 채식 판정을 제거했다. 전체 재료 확인 없이 채식 필터에 넣지 않는다.

## 제안하는 순서

### 1. 매장 수집 범위부터 확인

지점·기간·판매단위·조건·공식 근거를 갖춘 행사와 수집 현황을 별도 관리한다. 화면에는 수집 건수, 재료 매칭 수, 추천에 실제 쓰인 수를 구분한다. 매칭하지 못한 상품도 내부 감사 목록에 이유를 보존한다. ALDI Nord는 공식 전단에서 신선식품까지 수집됐는지 먼저 보완해야 한다.

### 2. 후보는 재료 색인으로 찾고, 후기는 검증한 값만 사용

7만 개 레시피를 매주 전부 재수집하지 않는다. 재료/상태/부위 색인으로 후보를 조회하고, 조리 가능한 식사 후보와 원문이 충실한 후보를 먼저 추린다. 최초 데이터 정비 시 수집기를 고친 뒤 리뷰·평점의 출처를 분리해 보정한다. 이후에는 신규/변경/확인기간이 지난 후보만 원문을 확인한다.

조회수, 댓글 수, 요리 후기 수, 별점 평가 수를 별도 필드로 저장한다. 원문 Recipe ID·검증 시각·추출 방식이 없는 수치는 후기 랭킹에 사용하지 않는다. 검증된 0과 미확인을 구별한다. 근거가 없는 레시피도 재료가 적합하면 탐색 메뉴로 남길 수 있지만 인기 메뉴라고 부르지 않는다. `select-meal-publication-expansion.mjs --review-evidence VERIFIED_REVIEWS.json`은 검증 evidence가 없는 후보를 `review-unverified`로 보류한다.

### 3. 자격 검사와 정렬을 나눈다

먼저 실제 지점의 유효 할인상품, 정확한 재료 형태, 식사 종류, 필수 재료·수량·조리법을 검사한다. 반찬/아침/디저트/음료는 별도로 분류한다. 그 다음에 취향별 순위를 계산한다.

- 균형: 주재료 할인 기여도, 추가 구매 재료 수, 조리 부담, 최근 반복을 함께 본다.
- 인기: 확인된 후기 수와 평점을 결합하되 1개의 별점 5.0이 수십 개의 좋은 후기를 쉽게 이기지 않도록 표본 크기를 반영한다. 후기 없음은 별도 표시한다.
- 가성비: 선택 인분의 누락 재료 전체를 살 포장 비용과 집에 있는 재료를 반영한다. 일부 재료 가격만 있으면 확인된 소계와 누락 수를 표시한다.
- 영양/다이어트: 출처 있는 영양값을 선택 인분으로 계산할 때만 수치 순위를 제공한다. 데이터가 없으면 가능한 대안은 '튀김 제외', '채소 포함' 같은 조리/재료 조건이며 영양점수로 바꿔 부르지 않는다.

임의의 가중치로 먼저 순위를 고정하지 않는다. 대표 메뉴 비교 사례에서 사용자가 납득하는 순서를 확인한 뒤 가중치를 정한다. 모든 카드에는 '어떤 할인상품', '어떤 확인된 후기', '추가 구매 부담', '미확인 항목'을 설명한다.

### 4. 주간 구성은 개별 메뉴 순위와 별도로 조합

메뉴마다 점수순으로 14개를 넣는 대신 식단 전체의 중복·공유 재료·포장 잔량·요일별 조리 시간을 본다. 수동으로 선택한 메뉴는 유지한다. X는 같은 조건에서 다른 후보를 제안하고, 후보가 없으면 이유를 표시한다. 글자 수 때문에 제목을 줄이지 않으며 월~일을 가로 7열, 점심·저녁을 세로 2칸으로 보여준다.

## 완료와 남은 작업의 경계

이번 변경: 게시된 레시피의 후기 원문 재검증 및 표시, 미확인 상태, 가로 요일 플래너, 수집/재료매칭 건수 구분. 기존 정적 JSON은 변경하지 않고 동일 스냅샷/상세에 묶인 검증 자료를 별도 제공한다.

다음 알고리즘 작업: 온톨로지 수집기 수정과 오염 필드 재수집, 후기 기반 후보 조회/게시 선정 재실행, main/side/dessert 재분류, 공식 할인 수집 보완, 검증된 가격·영양 데이터 확대. 이 단계 전에는 현재 후보 구성을 후기 상위 결과라고 주장하지 않는다.

## 재발 방지

`node scripts/verify-meal-reviews.mjs`는 현재 게시된 원문만 3개씩 확인하고 메타데이터 파일을 생성한다. 이후 `node scripts/sync-meal-pages.mjs`로 캐시 버전을 갱신한다. 새 스냅샷/상세 해시가 다르면 이전 검증값을 재사용하지 않는다. 테스트에는 다른 추천 카드의 4.9(1,077), 조회수, 댓글 0, 실제 후기 6, 상충 값, 상세 해시 변경 사례를 유지한다.

`node scripts/audit-meal-reselection.mjs`로 현재 5,000개 후보 보고서를 verified evidence 게이트에 다시 통과시킨 결과, 기존 승인 84개는 등록 상태로 제외되고 신규 후보 4,916개는 `review-unverified`로 보류됐다. 새 레시피를 자동 게시하지 않은 것은 데이터 부족을 숨기지 않는 정상적인 결과다. 온톨로지의 기존 숫자를 교체하는 DB 트랜잭션은 별도 승인 없이는 실행하지 않는다.
